# Prophet 协作记录与交付物

> 用途：记录项目中的可共享思考、决策依据、待验证问题和实际交付物，方便两位协作者在同一个上下文中推进工作。
>
> 更新规则：每次讨论后追加一条思考记录；每完成一个可以运行、查看或验证的结果，就在交付物表中登记。记录结论和依据，不记录任何密码、Token、原始用户数据或其他敏感信息。

## 如何使用

### 思考记录

每条记录包含：日期、问题、当前结论、对项目的影响、待验证事项。结论发生变化时不要覆盖旧记录，追加一条新记录并链接到旧记录。

### 交付物记录

每个交付物需要有负责人、状态、仓库路径或演示入口、验收标准。状态只使用：`待开始`、`进行中`、`待验收`、`已完成`、`阻塞`。

### 每日同步

每天结束时，两位协作者共同完成三件事：

1. 更新当天的思考记录；
2. 更新交付物状态并附上证据；
3. 写下第二天唯一最重要的目标和当前阻塞点。

## 第一部分：思考与决策记录

以下记录整理自 2026-09-07 至 2026-09-08 的项目讨论。它记录的是可共享的决策和依据，后续可继续追加完整的问答摘录。

### 2026-09-07：同步仓库并确认项目状态

- 问题：同事上传了什么内容，仓库是否已经有可运行项目？
- 结论：仓库已从 `https://github.com/Hsuehtan/prophet.git` 同步到本地，当前 `main` 为提交 `2c1755b`。仓库主要包含 MVP 需求文档，还没有应用代码。
- 依据：`README.md` 和 `docs/ideas/universal-growth-analysis-agent-mvp.md`；`dev`、`prod` 分支也只有初始化内容。
- 影响：当前工作应先做一个可演示的最小闭环，而不是直接假设已有前后端或埋点 SDK。
- 待验证：首个业务场景、数据来源、技术栈和真实测试数据尚未确定。

### 2026-09-07：理解项目目标

- 问题：Prophet 想解决什么问题？
- 结论：它计划成为通用增长分析 Agent。用户提供业务背景和行为数据，系统在确认业务定义、检查数据质量并进行确定性计算后，输出最多三条有证据、可执行的增长机会。
- 核心原则：程序负责计算事实，Agent 负责编排工具、解释证据和组织报告；事实、推测和经验规则必须区分。
- 影响：不能让模型自由猜指标或凭空生成数字；Business Manifest 和分析工具是可信度的基础。

### 2026-09-07：行为 CSV 从哪里来

- 问题：方案中的行为数据 CSV 由谁产生？
- 结论：原文档默认客户已经有埋点或业务数据，并从埋点平台、数据库、电商后台或 CRM 导出 CSV。只有订单表时通常无法还原完整行为漏斗。
- 影响：CSV 上传只能服务于已有数据的客户，不能解决没有埋点的客户的数据来源问题。
- 待验证：首批客户现在使用什么埋点或业务系统，能导出哪些字段，是否允许上传脱敏数据。

### 2026-09-08：补齐埋点前置环节

- 问题：如果项目本来要做埋点，没有埋点的用户从哪里得到行为数据？
- 结论：原方案把“实时数据采集 SDK”排除在 MVP 外，与产品目标存在缺口。完整流程应该包含：明确目标 → 设计埋点 → 接入并验证 → 积累数据 → 分析 → 行动验证。
- 重要区分：页面点击等通用行为可以由 SDK 辅助采集；注册成功、支付成功、预约完成等业务事件需要业务代码或服务端确认。
- 影响：后续产品范围需要明确两种入口：已有数据客户可上传 CSV；没有埋点的客户需要先获得埋点方案、接入方式和验证报告。
- 待验证：是否把埋点设计与质量检查作为首个 MVP 的核心，还是先用模拟数据验证分析内核。

### 2026-09-08：与普通分析平台和通用 AI 的差异

- 问题：用户已有分析平台，也可以直接问 AI，为什么还要使用 Prophet？
- 结论：单纯的“上传 CSV 生成报告”竞争力不足。Prophet 的价值必须落在可持续的闭环：业务语义管理、埋点质量检查、确定性分析、机会排序、验证方案和行动结果反馈。
- 预期差异：普通平台擅长展示指标，通用 AI 擅长解释用户提供的材料；Prophet 应该长期保存业务口径，判断事件是否正确，检查替代解释，并跟踪建议是否被执行。
- 影响：首版不应追求通用 ChatBI，而应选择一个场景，做出从数据可信度到行动验证的一条完整链路。
- 待验证：客户是否愿意为“更可信的判断和行动闭环”而不是另一套图表付出接入成本。

### 2026-09-08：三天协作方案

- 问题：两位协作者如何在三天内产出结果？
- 结论：先固定电商购买漏斗，目标是完成“CSV → 数据质量检查 → 漏斗分析 → 一条机会报告”的演示闭环。
- 分工：一位负责产品、数据、Manifest、规则和验收；另一位负责数据读取、质量检查、分析函数、报告生成和运行入口；每天共同集成和复现。
- 范围控制：暂不做完整 SaaS、实时 SDK、多租户、复杂前端、多 Agent 和开放知识库。
- 影响：三天后的交付物是可以验证方向的原型，不是生产系统。

## 下一阶段计划

### 第一天

冻结电商场景、Business Manifest、标准事件模型和三类测试数据；同时搭好读取入口、校验框架和日志配置。

### 第二天

实现数据质量检查、漏斗计算、设备或渠道对比、第一条场景规则和结构化报告。模型如需接入，只负责解释已有结果，不负责计算数字。

### 第三天

用正常、异常和错误数据验收，补齐 README、错误提示和演示材料，并根据结果决定下一步优先做埋点 SDK、真实数据连接还是第二个业务场景。
