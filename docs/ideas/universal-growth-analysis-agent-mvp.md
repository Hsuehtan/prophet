# 通用增长分析 Agent — MVP 需求文档 V0.1

## 1. 产品目标

让拥有业务行为数据，但缺少专业分析能力的经营者，通过上传数据和业务背景，在较短时间内获得一份：

- 与业务目标相关；
- 有数据证据；
- 明确区分事实与推测；
- 能说明优先级；
- 具备具体行动建议；

的增长机会报告。

MVP 主要验证：

> 用户是否认为 Agent 给出的机会判断可信、合理，并愿意据此采取行动。

MVP 不验证自动修改代码，也不以实际收入提升作为必要验收条件。

## 2. 推荐方向

MVP 采用以下组合：

> 通用分析内核 + Business Manifest + 报告型 MVP

架构层保持业务场景与客户技术栈无关，但产品验证阶段优先选择数据结构清晰、反馈周期较短的场景。

源码语言无关不等于接入实现无关，分析引擎通用也不等于业务判断天然通用。系统采用统一数据协议和分析算子，通过语言适配层处理接入差异，通过 Opportunity Pack 处理业务语义和建议差异。

整体结构：

```text
客户数据与业务材料
  ↓
Business Manifest：表达业务目标与业务语义
  ↓
统一事件模型
  ↓
通用分析内核：计算事实
  ↓
Opportunity Pack：提供场景判断和建议依据
  ↓
Agent：编排工具、组织证据并生成报告
```

## 3. 目标用户

首批用户应满足：

- 有明确线上转化目标；
- 已积累一定行为和转化数据；
- 当前依赖人工、表格或通用 Analytics 工具分析；
- 缺少专职数据分析师或增长团队；
- 能说明自己的业务目标、转化路径和关键指标；
- 愿意上传脱敏后的业务数据及背景资料。

架构不限定电商或技术栈，但首批测试建议选择以下数据结构较清晰的场景：

- 电商购买转化；
- B2B 留资或预约；
- SaaS 注册、激活或试用转化。

## 4. 核心用户流程

```text
创建分析项目
→ 上传业务背景文件
→ 上传埋点数据
→ Agent 生成 Business Manifest
→ 用户确认或修正业务语义
→ 系统检查数据质量
→ 确定性分析工具计算事实
→ Agent 发现并排序 Opportunity
→ 生成机会报告
→ 用户评价可信度与行动意愿
```

关键控制点：

> Agent 必须先正确理解业务，再分析数据；不能把字段名猜测直接当成事实。

## 5. MVP 功能范围

### 5.1 分析项目

用户可以：

- 创建一个分析项目；
- 设置项目名称和业务类型；
- 填写主要业务目标；
- 上传业务背景与数据文件；
- 查看当前处理状态；
- 查看最终 Opportunity 报告。

MVP 只支持单用户、单项目分析，不做团队协作和复杂权限体系。

### 5.2 业务上下文上传

支持上传：

- Markdown；
- TXT；
- PDF；
- CSV 格式的数据字典；
- 用户直接填写的文字说明。

业务材料可以包括：

- 公司和产品介绍；
- 商业模式；
- 核心业务目标；
- 用户类型；
- 页面或产品说明；
- 转化流程；
- 指标口径；
- 历史运营活动；
- 已知异常；
- 不允许采取的优化方式。

系统需要对文件进行解析、分段和检索，不能简单地把所有文本无差别塞入提示词。

每条知识应保留：

- 来源文件；
- 所在位置；
- 内容类别；
- 更新时间；
- 用户是否确认；
- 检索相关度。

### 5.3 Business Manifest

Agent 根据用户输入生成结构化 Business Manifest，至少包含：

```yaml
business:
  type: ecommerce | lead_generation | saas | custom
  primary_goal: purchase
  value_metric: revenue

objects:
  - product
  - order

conversion_funnel:
  - product_view
  - add_to_cart
  - begin_checkout
  - purchase

primary_metrics:
  - purchase_conversion_rate
  - revenue_per_visitor

segments:
  - device
  - traffic_source
  - country

constraints:
  - no_price_change
```

用户必须确认或修改 Manifest 后，系统才能开始正式分析。

验收标准：

- Agent 能从背景文件中生成结构化 Manifest；
- 每个关键定义能够追溯到用户材料或用户输入；
- 不确定的内容必须标记为“待确认”；
- 用户可以修改目标、漏斗、指标和 Segment；
- 未确认的核心指标不得用于生成正式结论。

### 5.4 数据上传与字段映射

MVP 支持 CSV，数据量上限暂定为单文件 500 MB。

最低字段要求：

- 事件名称；
- 事件时间；
- 用户 ID 或 Session ID；
- 至少一个业务行为字段。

可选字段：

- 页面；
- 组件；
- 设备；
- 国家；
- 流量来源；
- 商品或业务对象；
- 转化价值；
- 版本或发布时间。

系统自动推断字段含义，并生成从用户字段到标准字段的映射。用户确认后保存。

验收标准：系统能够识别并提示：

- 缺失字段；
- 无效时间格式；
- 重复事件；
- 空值比例；
- 异常事件量；
- 无法关联的用户或 Session；
- 转化事件缺失；
- 样本量不足；
- Manifest 中定义但数据中不存在的事件。

如果数据不足以支撑可信分析，系统应停止并说明原因，而不是勉强生成建议。

## 6. 通用分析内核

MVP 不需要完整的数据分析平台，但必须提供一组最小确定性分析 Function。它们用于保证事实可靠，不能全部推迟到后续版本。

### 6.1 数据质量工具

- `inspect_schema`
- `profile_dataset`
- `check_event_coverage`
- `check_missing_values`
- `check_duplicate_events`
- `check_tracking_anomalies`

### 6.2 指标计算工具

- `calculate_metric`
- `calculate_conversion_rate`
- `calculate_funnel`
- `calculate_value_per_user`
- `compare_time_periods`

### 6.3 诊断工具

- `compare_segments`
- `find_funnel_dropoff`
- `find_significant_change`
- `estimate_affected_population`
- `check_sample_sufficiency`
- `check_basic_confounders`

Function 输出必须包含：

- 计算口径；
- 时间范围；
- 样本量；
- 结果；
- 对比基准；
- 置信度或稳定性判断；
- 数据质量警告。

LLM 不能自行编造指标或执行无法审计的心算。

## 7. MVP Opportunity 范围

通用模型可以预留五类 Opportunity，但 MVP 默认只启用两类。

### 7.1 转化漏斗异常

系统发现：

- 哪个转化阶段损失最大；
- 当前表现是否偏离历史基准；
- 涉及多少用户；
- 是否有足够样本；
- 可能影响哪个最终业务目标。

### 7.2 Segment Divergence

系统比较：

- Mobile 与 Desktop；
- 不同流量来源；
- 不同国家或地区；
- 不同业务对象；
- 用户定义的其他 Segment。

只有同时满足以下条件才形成 Opportunity：

- 差异达到配置阈值；
- 样本量充足；
- 与核心业务指标相关；
- 基础混杂因素不能完全解释；
- 存在至少一个可采取的行动方向。

以下三类只保留接口，不承诺首版实现：

- 关键组件低效；
- 关键元素不可见；
- 发布后的指标异常。

它们分别依赖组件曝光、可见性和发布版本数据，不适合作为第一批上传数据的强制要求。

## 8. Agent 工作流

MVP 建议采用受控工作流，而不是高度自主的多 Agent 系统：

```text
理解任务
→ 检索 Business Manifest
→ 检查数据质量
→ 选择分析工具
→ 获得确定性结果
→ 寻找替代解释
→ 检索场景知识
→ 生成候选 Opportunity
→ 评估影响、置信度和可行动性
→ 输出最多 3 条
```

Agent 可以决定调用什么工具，但不能：

- 绕过数据质量检查；
- 修改指标定义；
- 把推测描述为事实；
- 在没有工具结果时生成具体数字；
- 因为“看起来合理”而忽略样本量；
- 一次输出大量低优先级建议。

开源 Agent 框架只负责：

- 工具调用；
- 工作流编排；
- 状态管理；
- 重试；
- Trace；
- 结构化输出。

框架本身不构成核心竞争力。MVP 优先选择轻量、可观察、支持人工调试的方案，避免一开始引入复杂多 Agent 协作。

## 9. 场景知识库

场景知识库以 Opportunity Pack 组织：

```text
Opportunity Pack
├── 适用业务类型
├── 业务对象和指标
├── 检测前提
├── 异常判断规则
├── 常见混杂因素
├── 可能原因
├── 优化 Playbook
├── 禁用条件
├── 风险
└── 验证指标
```

MVP 可以由团队人工维护少量高质量知识，不建设开放式知识库平台。

Agent 在使用知识时必须：

- 标明使用了什么场景规则；
- 区分数据证据与知识库经验；
- 确认建议满足适用条件；
- 在存在禁用条件时放弃建议；
- 找不到可靠知识时明确表示不确定。

## 10. Opportunity 报告

每次分析最多输出 3 条 Opportunity，默认突出最重要的一条。

每条报告必须包含：

1. **发生了什么**：由数据工具计算出的事实。
2. **为什么重要**：与用户核心目标的关系。
3. **影响范围**：涉及用户、转化或价值规模。
4. **关键证据**：指标、样本量、时间范围和对照。
5. **替代解释**：可能的混杂因素及检查结果。
6. **可能原因**：明确标记为 AI 推测。
7. **建议行动**：具体、有限、可执行。
8. **预期影响指标**：行动希望改变什么。
9. **风险与 Guardrail**：不能被牺牲的指标。
10. **置信度**：高、中、低以及判断依据。

禁止输出“优化体验”“增强信任”“提升视觉层级”一类不可执行建议。

## 11. 用户反馈与核心指标

每条 Opportunity 要求用户反馈：

- 数据结论是否准确；
- 原因解释是否合理；
- 建议是否可信；
- 是否愿意执行；
- 不认可的原因；
- 实际是否采取行动。

建议的 MVP 成功标准：

在不少于 5 个真实项目、累计不少于 30 条有效 Opportunity 的测试中：

- 数据结论认可率不低于 80%；
- 建议可信率不低于 60%；
- 行动意愿率不低于 40%；
- 严重事实错误率不高于 5%；
- 无足够证据时正确保持沉默的比例不低于 90%；
- 用户能够理解报告且不依赖分析人员二次解释。

以上为初始建议阈值，后续根据首批客户的数据量调整。

北极星验证指标：

> 每个完成分析的项目中，被用户认定为可信且愿意采取行动的 Opportunity 数量。

## 12. 关键假设

### 12.1 必须成立

- 用户愿意提供足够的数据和业务背景；
- Business Manifest 能正确表达不同业务的转化逻辑；
- 通用分析算子能够跨场景复用；
- 用户信任有证据、有限且克制的建议；
- 场景知识能够有效降低建议的泛化和空洞程度。

### 12.2 可能杀死产品的因素

- 上传数据质量普遍不足；
- 用户无法准确描述指标口径；
- Agent 的建议只是常识，没有新增价值；
- 跨场景抽象导致报告失去业务针对性；
- 为了表现“智能”，系统输出证据不足的结论；
- 用户认可建议，但没有足够动力采取行动。

### 12.3 验证方法

- 用同一分析内核测试至少两个业务场景；
- 每条报告由用户和内部分析人员分别评分；
- 保存所有工具调用、证据和最终结论；
- 对不可信报告进行错误归因；
- 区分数据错误、Manifest 错误、分析错误、知识错误和表达错误。

## 13. 明确不做

- **自动修改客户代码**：当前只验证建议可信度。
- **自动上线和回滚**：不属于核心假设。
- **Before/After 效果归因**：可记录行动，但不作为 MVP 必需闭环。
- **实时数据采集 SDK**：先使用文件上传验证分析价值。
- **支持所有五类 Opportunity**：没有相应数据时无法可靠判断。
- **任意自然语言数据分析**：容易退化成通用 ChatBI。
- **Dashboard 和自定义图表**：用户购买的是判断，不是制图工具。
- **多 Agent 自主讨论**：增加复杂度，但不会自然提高准确率。
- **用户自由创建工具和工作流**：首版由系统控制分析路径。
- **大规模开放知识库**：先验证少量高质量知识是否有效。
- **收入提升承诺**：当前尚未完成真实效果验证。

## 14. 推荐实施顺序

1. 定义标准事件模型和 Business Manifest；
2. 准备两类匿名真实数据集；
3. 实现数据检查和基础分析 Function；
4. 人工编写首批 Opportunity Pack；
5. 建立受控 Agent 工作流；
6. 输出结构化报告；
7. 增加用户反馈；
8. 用真实客户数据验证可信度；
9. 根据错误类型决定下一步补数据工具、知识库还是接入 SDK。

## 15. 开放问题

- MVP 的开发周期、团队人数和角色配置是什么？
- 首批用户的数据通常来自埋点平台、数据库还是人工导出？
- 单次分析允许等待多长时间？
- 用户上传的数据是否包含个人信息，需采用什么脱敏和留存策略？
- 首批 Opportunity Pack 选择电商、B2B 留资还是 SaaS 激活？
- 用户反馈由站点老板本人提供，还是由运营、产品或技术负责人提供？
